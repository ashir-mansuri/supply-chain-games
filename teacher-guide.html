Teacher’s guide

Two games, each built to fill one 60-minute class: about half the time playing and the rest discussing what happened. Students learn more from the debrief than from the game itself, so protect that time.

Running a session

Each game can be played in two ways:

  • Online team play. Every student uses their own phone or laptop. Team members log in with the same team name and PIN, and their screens stay in sync. In Supplier Showdown each member manages some of the four parts, and orders go out only when every member taps Ready. In Warehouse Rush members take turns as the picker while the others help plan the route. Your teacher dashboard shows every team’s progress and score live. This works in a classroom and in an online class on Google Meet or Zoom (put teams in breakout rooms so they can talk). It needs the one-time setup below.
  • Practice on one device. A team gathers round one phone or laptop. No setup or class code is needed, and it works even if online play isn’t switched on. You type each team’s result into the practice scoreboard on your projector.
  • Devices. Any phone, tablet or laptop with an up-to-date browser (Chrome, Safari, Edge or Firefox). Nothing to install. Laptops and tablets show the warehouse map larger.
  • Teams. 3 to 5 students for Supplier Showdown (it rewards discussion); 2 to 4 for Warehouse Rush.
  • Same events for everyone. All teams in one online class face the same news (Supplier Showdown) or the same warehouse and orders (Warehouse Rush), so results compare fairly. For practice games, write one game code on the board instead.
  • Don’t use private or incognito windows. The game remembers a student’s team in the browser, so they can rejoin after a refresh.
  • Privacy. Online, the only personal detail stored is the first name a student types, in your own Firebase project, until you delete the class. Practice games store nothing outside the device.

All companies, products, prices and events are made up for teaching. They are realistic in direction (Chinese parts are cheaper but further away and riskier; local parts cost more but arrive faster) but not real market data.

Online team play

Online play needs a small free database so that phones can share a game. The site uses Google Firebase, which is free for a class of this size: up to 100 devices connected at once (enough for about 90 students plus your dashboard), with no payment card. You set it up once, in about 15 minutes, and it then works for every class.

One-time setup

  1. Create a Firebase project. Go to console.firebase.google.com and sign in with your Google account. Choose Create a project, name it supply-chain-games, turn off Google Analytics (not needed) and create the project.
  2. Create the database. In the left menu open Build > Realtime Database and choose Create database. Pick the location Singapore (asia-southeast1), the closest to India. Choose Start in locked mode and click Enable.
  3. Set the rules. Still in Realtime Database, open the Rules tab. Delete everything in the box, paste the rules below, and click Publish.

}
  4. Switch on anonymous sign-in. Open Build > Authentication, click Get started, go to the Sign-in method tab, choose Anonymous, switch it on and click Save. Students never see a login screen; this just lets the game talk to your database.
  5. Register the website. Click the gear next to Project Overview and open Project settings. Under Your apps, click the web icon (</>), type a nickname such as games, leave Firebase Hosting unticked and click Register app. Firebase shows a block of code that starts with const firebaseConfig = {. Copy that block, from const firebaseConfig down to };. Check that it has a line starting with databaseURL. If it doesn’t, copy the address shown at the top of the Realtime Database Data tab and add it as databaseURL: "https://…",.
  6. Paste it into the site. On GitHub, open your supply-chain-games repository and click firebase-config.js, then the pencil icon (Edit). Replace the line const firebaseConfig = null; with the block you copied. Click Commit changes. GitHub updates the site within a minute or two.
  7. Check it. Open the teacher dashboard. It should say Online play is switched on. Create a test class, join it from your phone, then delete it.

The firebaseConfig block is not a password. It only tells the games where your database is, and the rules decide what anyone can do. Students can only reach a class if they know its code, and only join a team with its PIN.

If the dashboard says it can’t connect: check that the rules were published, that anonymous sign-in is switched on, and that firebase-config.js has a databaseURL line. In Firebase, Authentication > Settings > Authorized domains should list your GitHub Pages address (for example ashir-mansuri.github.io); add it if it’s missing.

Want to try it first? On the teacher dashboard, choose Try demo mode. Online play then works inside your own browser only: open the game in two or three tabs and join the same team to see how teammates play together.

Running an online class

  1. Before class: open the teacher dashboard, choose Create a class, pick the game and the number of teams, and set a teacher password. You get a class code and a 4-digit PIN for each team. Rename teams if you like.
  2. Start of class: put the class code on the board or in the meeting chat, with the game’s web address. Give each team only its own PIN, for example on a slip of paper or by message.
  3. Students join: each student opens the game, chooses Join your team, enters the class code, picks their team, types the PIN and their first name.
  4. During play: keep the dashboard open. It shows who is online in each team, where each team has got to, and live scores. Projector view shows just the class code and the leaderboard.
  5. If a team gets stuck: Restart game on the dashboard starts that team again from the beginning. If a student drops out, their parts or picking turns pass to teammates automatically.
  6. After class: discuss the results on the projector, then Delete this class to remove the students’ names and results.

Supplier Showdown

Teams run purchasing for Sabar Scooters, an electric scooter maker in Sanand. Each scooter needs four parts: a battery pack, a hub motor, a controller chip and a tyre set. Each can come from four suppliers: Shenzhen (China), Hanoi (Vietnam), Pune (India) and Stuttgart (Germany). The game runs from April to November. Every month teams split their orders between suppliers and choose a buffer stock level, and then a news card is drawn. The previous manager sourced everything from Shenzhen because it was cheapest, so every team starts there.

Learning outcomes

By the end of the class, students should be able to:

  1. Tell apart quoted price, landed cost and total cost of ownership, and calculate each one.
  2. Compare single sourcing with dual or multiple sourcing in terms of cost and risk.
  3. Explain what buffer (safety) stock does and what it costs.
  4. Explain why the scarcest component limits output when a product needs several parts.
  5. Argue a position on the trade-off between efficiency and resilience, using evidence from the game.

60-minute lesson plan

0–8Hook and rules. Ask: “If one supplier is 25% cheaper, why would anyone buy from the other?” Take a quick show of hands. Project the start screen and go through the four rules in the box. Write the game code on the board.
8–10Teams start. Online: students join their team with the class code and PIN. Practice: each team opens the game on one device and types the game code.
10–40Play eight months, about 3 to 4 minutes per month. Keep the class roughly together: call “two minutes to place orders”. Walk around and ask teams to explain their split. Don’t give away what is coming.
40–52Results and debrief. Show the leaderboard (online, it is already on your dashboard; for practice games, type each team’s result into the practice scoreboard). Ask two contrasting teams to explain their strategy. Then work through the discussion questions on the final report (answers below).
52–60Theory wrap-up. Put the total-cost formula on the board, connect dual sourcing and buffer stock to the risk the class just lived through, and set the follow-up task.

Short on time? Give about 2 minutes per month after the first two. Teams speed up once they know the screens. The final report, with its comparison against three fixed strategies, appears after all eight months.

How the game works

Demand. The planning screen shows the dealers’ forecast (950 in April, rising to 1,400 in October’s festive season). Actual orders land within 6% of the forecast, plus any news effect.

Online teamwork. The four parts are shared out among the team members who are online (with two members, each manages two parts). A member can change only their own parts; anyone can change the buffer stock, which asks everyone to confirm again. The month is played when every member online has tapped Ready.

Ordering. Teams don’t type quantities. The game orders forecast + buffer target − stock in hand, for each part, and splits that order by the percentages the team chose. This keeps the focus on the sourcing decision. Orders arrive within the month; lead time shows up as the cost of money tied up in transit and as how long a disruption lasts.

Production. Scooters built = the smallest of (dealer orders, and stock plus good arrivals for each of the four parts). One missing part stops the line, however much of the others is in the store.

New suppliers. Approving a supplier for a part costs ₹5 lakh once, and it ships only half its share in its first month. Switching after a crisis is slow and costly; diversifying before one is cheaper.

Capacity. Pune can supply at most 60% of battery packs and 40% of chips, so a fully local strategy isn’t possible.

Reliability and quality. Each month a supplier may ship slightly short (on average about 7% for Shenzhen, 5% Hanoi, 3% Pune, 1% Stuttgart). Faulty parts, at around each supplier’s defect rate, are paid for and scrapped.

Money.

Selling price to dealers₹75,000 per scooter
Assembly and other variable cost₹12,000 per scooter built
Fixed costs₹1.5 crore per month
Dealer penalty₹5,000 per scooter not delivered (plus the lost sale)
Storing stock2% of part price per month

Approving a new supplier₹5 lakh per supplier per part, once

Monthly profit counts the parts actually used (at average cost), not the cash spent on restocking, so building a buffer doesn’t show up as a loss in the month you buy it.

Every game has the same pattern: a quiet April, a major China disruption in June or July, a Pune disruption in August or September (with a warning on the planning screen that month), one global shock, one quality problem and the October festive rush. Debrief: answer points

1. Which month hurt you most? What could you have done before it happened?
Usually the China disruption month. Teams that had already approved a second supplier and held some buffer lost far less. Reacting after the event is too late: new suppliers ship only half in month one and cost ₹5 lakh each. Point: resilience must be bought in advance, like insurance.
2. Compare quoted price with landed cost. What else did cheap parts cost you?
Duty and freight shrink the price gap; transit time ties up money; higher defect rates mean paying for scrap; and the long, risky supply line caused lost sales and dealer penalties. This is total cost of ownership: the cheapest quote is rarely the cheapest supplier.
3. A new supplier ships only half in its first month. What does that mean for switching after a crisis?
Qualifying a supplier takes time (audits, samples, ramp-up). In a crisis every buyer is switching at once, so capacity is scarce too. Keep a second supplier active, even at a small share, so it can be scaled up.
4. When was buffer stock worth what it cost?
When it covered a short disruption or the festive demand spike. It was wasted when nothing went wrong, and it can’t cover a long outage like a two-month fire. Buffer stock handles short, uncertain gaps; dual sourcing handles long ones.
5. Which part was your weakest link?
Often the battery pack (biggest cost, Pune capacity cap) or the chip (shortage event, Pune capped at 40%). In assembly, output is set by the scarcest part, so risk must be managed part by part, not just for the most expensive one.
6. What would you tell the board about cheap versus safe?
A good answer weighs both: a modest cost premium for a second source and a small buffer protects revenue worth far more. Strong answers use numbers from their own game, such as profit lost in the worst month compared with the cost of diversifying.

Follow-up work

  1. Total cost worksheet. Using the supplier table above, calculate landed cost and true cost per good part for each battery supplier. Which supplier wins on quoted price, and which on true cost?
  2. Weighted supplier scorecard. Score the four motor suppliers out of 10 on cost, quality, delivery and risk. Weight them 40/20/20/20, then 25/25/25/25. Does the winner change?
  3. Memo to the board. One page: recommend a sourcing strategy for next year, with evidence from the game and one real-world example of a supply disruption.

Warehouse Rush

Teams are pickers at a fulfilment centre near Ahmedabad during the festive sale. The warehouse has four aisles (A to D), each with eight bays on both sides: 64 slots holding 36 products. Teams pick the same six customer orders three times. In round 1 the layout is random. In round 2 they first study last month’s sales and re-slot the warehouse. In round 3 they batch-pick two orders per trip. After every trip the game shows the shortest possible route for the same shelves.

Learning outcomes

  1. Carry out an ABC analysis on sales data and explain the Pareto pattern.
  2. Explain how slotting fast movers near dispatch cuts travel time.
  3. Compare single-order picking with batch picking, including the trade-offs.
  4. Measure picking productivity in lines per hour and break picker time into its parts.

60-minute lesson plan

0–8Hook. Ask: “What does a picker spend most of their shift doing?” (Usually walking.) Show the start page and how picker time is counted. Write the code on the board.
8–18Round 1: Day one. Six orders on a random layout. Let teams notice how far apart the shelves are. Online, team members take turns as the picker, one trip each, while the others call out the route.
18–28ABC analysis. Everyone pauses at the sales chart. Ask: what share of picks do the top 7 products make? (67%.) Teams then re-slot by tapping shelves. “Do it for me” shows the ideal layout if a team is stuck.
28–36Round 2: ABC slotting. The same six orders on the new layout.
36–44Round 3: Batch picking. Three trips of two orders each.
44–56Debrief. Leaderboard first (round 1 and round 3 lines per hour; online it is on your dashboard), then the discussion questions on the results screen.
56–60Wrap-up. Connect to real warehouse practice and set the follow-up task.

How it works

  • Picker time per trip = 20 seconds setup + 10 seconds per line + walking distance ÷ 1.2 metres per second.
  • Lines per hour = lines picked ÷ total picker time × 3,600.
  • Walking follows the aisles: up and down an aisle, and between aisles only along the front or back cross-aisle. Every trip starts and ends at dispatch.
  • Shortest route is calculated exactly for each trip, so route efficiency (shortest ÷ yours) is a fair measure of route planning.
  • ABC classes: A = top 7 products (20% of products, 67% of picks); B = next 11 (19% of picks); C = last 18 (14% of picks).
  • Fast-pick zone: the 8 slots nearest dispatch, outlined in gold on the re-slotting map.
  • Walk per pick on the re-slotting screen is the average round trip from dispatch to a product, weighted by how often it sells. It drops from about 38 m on a random layout to 20 m on the best layout.

With perfect routes, the same orders run at about 112 lines per hour in round 1, 143 in round 2 and 186 in round 3 (average across test games). Students’ round 1 is usually lower, because routes are harder to plan when shelves are scattered.

Debrief: answer points

1. How much of the gain came from slotting, and how much from batch picking?
Compare rounds 1–2 (slotting only) with rounds 2–3 (batching only). Slotting cuts metres per line; batching cuts trips, so it saves setup time and walks back to dispatch.
2. Why does the Pareto pattern make ABC slotting so powerful?
Because a few products make most of the picks. Moving 7 products close to dispatch affects two-thirds of all picks, while moving the 18 C products barely matters.
3. Was your route close to the shortest one? When was it hardest to plan?
Hardest with many stops spread over several aisles, which is why real warehouses use routing rules (such as the S-shape route) or software. A good layout also makes routes easier, not just shorter.
4. When would batch picking not be worth it?
When orders must be sorted afterwards (extra time and errors), when orders are urgent and can’t wait to be grouped, or when orders are large enough to fill a trolley alone.
5. How often should a warehouse re-slot?
Demand changes with seasons and promotions (festive gifting, monsoon goods). Re-slotting costs labour and can disrupt picking, so warehouses re-slot the few products whose class has changed, often seasonally.
6. Where else could you save time?
Setup and pick time per line (scanners, pick-to-light), zone picking, better racking heights (the “golden zone” at waist height) and the building layout itself, such as dispatch placement.

Follow-up work

  1. ABC in a spreadsheet. Give students a list of 50 products with monthly sales. They sort, calculate the running share and draw the Pareto chart, then propose A, B and C cut-offs.
  2. Productivity sum. A picker does 140 lines an hour on an 8-hour shift with 1 hour of breaks. How many pickers are needed for 6,000 lines a day? What if batch picking raises the rate to 185?
  3. Site visit or video reflection. Watch a warehouse tour video and identify the picking method, the slotting logic and one improvement.
